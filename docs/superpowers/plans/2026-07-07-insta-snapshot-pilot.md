# Insta Snapshot Testing Pilot — Help Overlay Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Introduce the `insta` snapshot-testing crate with one minimal, high-signal test case — the F1 help overlay — so the team can evaluate the workflow before adopting it broadly.

**Architecture:** Add `insta` as a dev-dependency and write a single snapshot test next to the existing help-overlay unit tests. The help overlay is the ideal pilot: its render function (`draw_help_dialog`) is already a pure `fn(&mut Frame, u16)`, the existing tests already drive it with a `TestBackend`, and its body is static keymap text — so the snapshot locks the entire keybinding reference with one `assert_snapshot!(term.backend())` call, and any future binding/rewording/layout change surfaces as an obvious diff.

**Tech Stack:** Rust (edition 2024, MSRV 1.88), ratatui 0.30 `TestBackend`, `insta` 1.x snapshot crate. No `cargo-insta` binary is required for this pilot (baseline seeding uses the `INSTA_UPDATE` env var, which the `insta` library reads directly).

### How insta snapshot tests differ from ordinary TDD (read before Step 3)

A snapshot test has a different RED/GREEN rhythm than assertion-based tests. The `insta` crate works like this:

1. You write a test that calls `insta::assert_snapshot!(value)`.
2. **First run:** no `.snap` baseline file exists yet. `insta` writes a sibling `<name>.snap.new` file with the actual output and the test **fails** (this is RED — but it fails because the baseline is missing, not because the assertion is wrong).
3. You accept the baseline. For this pilot we accept non-interactively by running with `INSTA_UPDATE=always`, which promotes the output into the committed `<name>.snap` file.
4. **Second run (no env):** `insta` finds the committed `.snap`, compares, matches → test **passes** (GREEN).

After that the `.snap` file is a committed test asset. When someone later changes the help overlay intentionally, the test goes red, and they accept the new output (`cargo insta review` interactively, or `INSTA_UPDATE=always` for this pilot). An unintentional change just stays red and gets caught.

```rust
    #[test]
    fn draw_help_dialog_renders_first_page() {
        // Snapshot the help overlay at scroll 0. The dialog chrome (MAX_H=24
        // in `dialog`) caps the body at ~20 rows regardless of terminal size,
        // so this locks the dialog GEOMETRY (centering / border / " help "
        // title / "↑↓ scroll · F1/Esc close" footer) and the FIRST keymap page
        // (Tabs through Settings) — not the full keymap. The complete keymap
        // text is already covered by `help_lines_cover_every_surface_*` above;
        // this snapshot's job is render regression (layout, footer wording,
        // first-page bindings). Accept intentional changes via
        // `cargo insta review` (or, for this pilot, `INSTA_UPDATE=always cargo
        // test ...`).
        let backend = TestBackend::new(100, 40);
        let mut term = Terminal::new(backend).unwrap();
        term.draw(|f| draw_help_dialog(f, 0)).unwrap();
        insta::assert_snapshot!(term.backend());
    }
```

> **MAX_H reality (discovered in implementation):** an earlier draft of this plan assumed a 100x40 terminal fits the full keymap. It does not — `dialog::MAX_H = 24` caps the dialog body at ~20 rows regardless of terminal size, so the snapshot captures the first scroll page, not all 33 `help_lines()`. That is still a useful render-regression lock; the full keymap TEXT remains covered by the existing `help_lines_*` unit tests. Do NOT try to "fix" this by bumping the terminal height — the cap is in the dialog chrome, not the test.

## Notes for the reviewer / user after execution

- **What to look at to judge "is insta worth it":** open `src/tui/snapshots/<name>.snap`. That single text file is the entire help overlay, locked. Edit any binding in `src/tui/help.rs::help_lines()`, rerun the test, and watch it go red with a precise diff — that is the value prop.
- **This pilot is non-invasive:** if you decide not to adopt insta broadly, reverting is two commits (`git revert`) and removes the dev-dependency. No production code path changed.
